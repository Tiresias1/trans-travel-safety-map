### Findings

**P1 — `runner.py:140` (+ dispatch call `runner.py:1739`): the 11000-token output budget is incompatible with the unchanged 30 s transport timeout, which will very likely kill stage one as an unreconciled liability.**
Evidence: v2 kept v1's `TIMEOUT_SECONDS = 30.0` while raising `max_tokens` 2000 → 11000. The only pinned scoring attempt (`call-001.json`) took **28 s** (`requested_at 04:19:25` → `finished_at 04:19:53`) for 2000 completion tokens and still ended `finish_reason: length` — i.e. ~70 tok/s, so an 11000-token non-streaming generation needs ~2 min of server-side silence, far past 30 s of socket silence. A read timeout raises `Refusal(EXIT_STOPPED, "transport error …")` with `raw = None` → `parse_billed` returns `cost: None` → `unreconciled_liability` → the whole stage stops **and** every later run refuses ("requires a new reviewed version"). Smallest fix: predeclare and disclose an explicit, bounded transport timeout as part of the settings-change disclosure (it is currently mentioned nowhere in `protocol.md`/`manifest.json`), or stream, before the receipt binds this code. Caveat: not executable-offline-provable here; it is a design/feasibility defect, not a fail-open.

**P1 — `verify_manifest` (`runner.py:513-534`, `599-602`): prompt byte-identity "both ways" (claimed in `protocol.md` §3: "The runner verifies byte-identity both ways; drift refuses") is not enforced for `single_a.txt`/`single_b.txt`.**
Evidence: v2 prompt bytes are only checked against `manifest.files[...]["sha256"]` (523), the *v1 originals* are checked against `V1_SOURCE_PINS` (527-533), and `source_v1_frozen_byte_identity[...]` is checked only as a manifest *claim* against the pin (599-602). There is no assertion that `files["single_a.txt"]["sha256"] == V1_SOURCE_PINS["frozen/single_a.txt"]`. A prompt **plus** its manifest entry co-tampered therefore passes every runner gate (the receipt only records whatever hashes exist; `test_runner.py:376-382` tampers the prompt but not the manifest, so the gap is untested). Messages are genuinely checked both ways in `verify_schedule`; prompts are not. Smallest fix: 2-line cross-check of `files[...]` against `V1_SOURCE_PINS` for the two prompts + a co-tamper test.

**P1 — test suite has no real cross-process lock race test (explicit review item).**
Evidence: `grep multiprocessing|subprocess|Popen|fork|Thread|race|spawn` over `country-feasibility-v2/` → **no matches**. `SharedLockTests` (`test_runner.py:283-333`) only contends within one process and only checks that a foreign/stale lock is refused and that a different `holder`/`pid` is not deleted. The `O_EXCL` atomicity across two processes — the single safety mechanism shared with v1 — is never exercised. Smallest fix: a test that spawns a second process (or `os.fork`) contending for the same lock file and asserts exactly one winner plus pid-scoped release.

**P1 — `cell_key` reads a field real attempt records do not contain, so the tested "cell already attempted" gate is unreachable on real data (`runner.py:1079-1081` vs `runner.py:1721`).**
Evidence: attempt records store `"requested_model": row["model"]`, never `"model"`; `prior_v2_state` computes `cell_key(rec)` (1008) → `model=None` for every real record, so `prior_gate_v2`'s overlap check can never match, and two prior cells differing only by model collide into a false "re-attempted cell". Safety is *not* lost — the blanket gate `if v2_prior["runs"]: raise` (`runner.py:1578-1583`) refuses regardless — but `test_attempted_cell_blocks_new_run` (`test_runner.py:856-869`) feeds a raw **schedule row** as the attempt file, i.e. a shape the runner never writes, asserting a message real runs cannot produce. Smallest fix: `cell_key` should read `model` or `requested_model`, and the test should use a real attempt record.

**P2 — `native_finish_reason` is never validated (`runner.py:1496-1501`).** All five pinned raw bodies carry it (`stop`/`stop`, `length`/`MAX_TOKENS`, `stop`/`STOP`, `length`/`length`), yet a response with standardized `finish_reason: "stop"` and native `MAX_TOKENS`/`CONTENT_FILTER` would pass, contradicting the runner's own doctrine that prior-observed fields are required. Bounded by the output contract (truncated JSON still fails), so report-only; add a native-reason check or an explicit disclosure.

**P2 — the `_validate_usage` claim "all observed in the five reviewed prior records" is false for `reasoning_tokens ≤ completion_tokens` (`runner.py:1396-1403`, `1444-1448`; same rule in `protocol.md` §5.4).** The pinned v1 failure record itself reports `completion_tokens: 2000` with `completion_tokens_details.reasoning_tokens: 2504`. The rule is fail-closed (a v1-shaped truncated response stops anyway at `finish_reason`), but the "observed in all five records" justification misstates the evidence and could false-stop a `finish: stop` response if this provider ever reports reasoning above completion. Fix the wording/evidence base; keep the stop.

**P2 — `raw_response` is not byte-exact despite the comment "exact provider bytes" (`runner.py:1178`, `1779`).** The body is `decode("utf-8", "replace")`, so invalid sequences are silently substituted before storage; also there is no test asserting the credential never appears in written artifacts, no test for the transport-error→liability path (the timeout path above), no test for `_finalize_orphan`/`failed_closed`, and no test for `preflight.status != "signed_off"`.

### Unsupported assumptions / limitations of this review

- **Receipt authenticity is not verifiable by the runner**: there is no signature; whoever can write `preflight_receipt_v2.json` can assert `status: "signed_off"`, and the runner cannot distinguish an approving from a rejecting review document (only presence + hash). Disclosed in `protocol.md` §7 ("Binding bytes is not execution approval") — accepted as a stated limitation, but it means the receipt gate is only as strong as the human process.
- **Evidence provenance is inherited, not re-derived**: v2 copies v1's message bytes and pins `data/countries.json`, but never re-runs the v1 path-whitelist derivation; correctness of derivation rests on v1's reviewed records.
- **All pins are same-change constants**: `V1_SOURCE_PINS`, `V1_TREE_DIGEST`, `EXPECTED_PLAN` (66609/1112686) were authored in this change. `watchdog_diff` shows **only untracked files and no tracked modifications**, so the whole experiment tree has no committed baseline to corroborate them; I verified internal consistency (record values, ids, sums read from the raw files) but not the digests themselves.
- **I could not execute the test suite** (read-only review, no shell): `.testtmp` absent and no receipt/reviews exist, so the suite appears never run here. Supervisor command: `python3 research/experiments/country-calibration-audit/country-feasibility-v2/test_runner.py` (offline, no network/credentials; it transiently creates/removes the shared `.execution.lock` in the v1 dir).
- The 128-unit framing allowance and the local-only USD guard are disclosed assumptions, correctly labelled as not provider-guaranteed; the pilot2 "95/96 parseable calls at 11000" precedent was not re-verified (out of scope).

### Merge verdict: **BLOCK**

No fail-open safety defect was found in billing, dispatch, locking or credential handling — those are genuinely fail-closed and well tested. But four P1s must be fixed before this code is bound by a receipt: the undisclosed 30 s timeout vs the 11000-token budget (very likely to end stage one as a permanent unreconciled liability), the manifest/prompt byte-identity hole contradicting `protocol.md` §3, the explicitly required cross-process lock race test, and the dead `cell_key` gate masked by a test using a record shape the runner never writes.
